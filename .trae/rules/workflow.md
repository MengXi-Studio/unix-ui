# 功能实现工作流（文档驱动四步）

> 本规则定义「实现功能 / 修改行为」类任务的强制推进流程，与 `architecture.md`（管写什么）互补——本文件管怎么推进。
> 核心机制：**文档驱动**——需求分析、伪代码方案、疑问与回答、实施记录全部落盘到 `.trae/documents/` 的任务文档中，跨会话持久；对话只做通知与执行，**不在对话中回答疑问**。
> 触发条件：用户要求新增组件 / 演示页 / 文档页面，或扩展既有组件能力、修改既有行为。纯问答、架构讨论、文档编写不适用。

## 第一步：建立任务文档（需求分析与伪代码设计，写任何代码之前）

- 在 `.trae/documents/` 下按 **需求类型 / 日期** 两级目录归档任务文档：
  `.trae/documents/<需求类型>/<YYYY-MM-DD>/<组件名>-<功能名>.md`
  - 第一层（需求类型）：`新增`（新组件 / 新页面 / 新能力）/ `优化`（既有功能优化）；其它类型（如 `修复`）同层扩展；
  - 第二层（日期）：任务创建当日（`YYYY-MM-DD`），隔离不同任务的 md 文件，避免重名；
  - 文件名：`<组件名>-<功能名>.md`（如 `新增/2026-10-22/mxi-tag-基础组件.md`）；无法归到具体组件的用 `<功能名>.md`。
- 文档固定结构（首次创建时生成，后续步骤逐节填充）：

```markdown
# <功能名> 实施方案

## 需求
<用户原话要点与任务目标>

## 需求分析
<涉及的组件 / 包与文件 / 影响面：主题变量、演示页、双语文档、侧栏导航>

## 伪代码设计
<组件 props/events/slots 清单、模板结构、关键逻辑分支——不写最终可运行代码>

## 疑问清单
### Q1 <问题原文>（影响：<范围>）
回答：

## 实施记录
（实现完成后回填）
```

- 建档后在对话中告知用户文档路径，请其**在文档「疑问清单」的「回答：」处作答**。

## 第二步：等待并读取回答（跨会话循环）

- 用户回答后再次发起会话时：**读取任务文档完整内容**（不是只读自己写的段落），逐条核对疑问清单：
  - 仍有未回答的疑问 → 在文档中补充新疑问 / 细化问题，通知用户继续作答，**回到本步等待**；
  - 全部澄清 → 进入第三步。
- 判定标准：回答只认文档中「回答：」处的内容；对话里口头回答的，须由 AI 转记入文档后方可生效（保证文档自包含）。
- 本步可循环多轮，直到疑问清单全部闭环。

## 第三步：实现与验证（DoD 硬性门槛）

- 按 `architecture.md` 第 3 节的标准落码顺序实现（组件 → 主题 → 同步 → 演示 → 文档）；实现依据以任务文档为准（含用户的全部回答）。
- 实现过程中**新增**的疑问 → 写入任务文档疑问清单，回到第二步等待，禁止拍板。
- 验证（见 `architecture.md` 第 7 节）：
  1. `pnpm sync:uni-modules:check` 一致性通过；
  2. HBuilderX CLI 编译运行 playground，确认编译成功；
  3. 浏览器打开演示页实测全部变体（截图比对），无运行时错误；涉及主题覆盖的需在 uni.scss 定义 `$mxi-*` 变量后重启 server 再验；
  4. `pnpm build:docs` 死链检查通过；
  5. 清理临时调试代码，达到 core-protocol DoD。

## 第四步：实施记录回填（任务完成后，必须）

- **回填任务文档**的「实施记录」章节：
  - 方案落地形态（与伪代码设计的差异说明）· 变更文件清单 · 验证方式与结果 · 遗留 TODO（含位置；无则写「无」）。
- 同时向 `.trae/documents/implementation-log.md` 追加一行索引：日期 · 任务文档相对链接 · 一句话结果（保持全项目任务的汇总视图）。
- 用户可见变更登记 `playground/uni_modules/mxi-ui-x/changelog.md`（KEEP 文件，手工维护）；文档站更新日志页如收录该类目，同步更新。
- 回填完成才算任务闭环；「代码写完但未回填」视为未完成。
