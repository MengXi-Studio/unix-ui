# @meng-xi/unix-ui v0.4.1 发布：m-tabs 五连修复——五个「零报错」的坑，每个都要跑起来才能看见

> v0.4.1 是一个纯修复版本，聚焦 v0.4.0 新增的 m-tabs：五个 bug，**控制台全部零报错**——小程序端首屏无激活标签、下划线偏了半个条宽（两种成因）、标签栏根本滚不动、scrollspy 点击标签纹丝不动且激活态与内容错位。有的是平台 API 差异，有的是废弃属性叠加溢出裁剪，最隐蔽的一个：一行裸调用被 Web 构建静默解析到了 `window.scrollTo`。本文保留完整排查过程与修复代码。

## 一、为什么单独发一个修复版本

v0.4.0 发布 m-tabs 时，微信小程序端尚未实测（平台支持表里明确标注「本版本未实测」）。issue #5 的反馈在开发者工具里一跑就命中：**小程序端打开任何带 m-tabs 的页面，首屏没有激活标签、底部条不显示**。

顺着这条线索排查，最终确认了五个问题。它们的共同点是：编译期全部合法、运行期全部静默——编译器一个字都不会说，只有页面跑起来才能看见。都已源码层修复，Web 端既有行为不变。

| # | 问题 | 一句话根因 |
| --- | --- | --- |
| 1 | 小程序端首屏无激活态、底部条缺失 | 小程序端 UniElement 没有同步测量 API |
| 2 | 滚动 / 收缩布局下划线偏移半个条宽 | `left: 50%` 钉的是条左缘，没回退半宽 |
| 3 | 滚动布局标签栏无法滚动、激活标签贴边裁切 | `scroll-x` 废弃 + 中间层 overflow hidden 藏住溢出 |
| 4 | 带 nav 插槽时下划线偏移 | 均匀槽位公式的前提被插槽占位打破 |
| 5 | scrollspy 点击标签不滚动、激活与内容错位 | 裸调用解析到 `window.scrollTo` + 判定基准线混用两套坐标 |

## 二、坑 1：小程序端 UniElement 没有同步 getBoundingClientRect

**现象**：m-tabs 演示页在小程序端首屏无激活态、底部条缺失；控制台抛 `TypeError: el.getBoundingClientRect is not a function`。

**排查**：m-tabs 的 `measureWidth`、scrollspy 滚动判定、点击定位三处都在 mounted / 滚动链路里同步调用 `el.getBoundingClientRect()`。Web 与 App 端的 `UniElement` 都有同步测量，唯独小程序端只提供 `getBoundingClientRectAsync`（回调 Promise）——同步方法根本不存在，调用即抛错。

更麻烦的是抛错的位置效应：**`TypeError` 中断了同一 onMounted hook 内的后续初始化**，激活态计算、底部条渲染全部没执行。症状（首屏无激活标签）与出错代码（宽度测量）相距很远，仅看表象根本对不上号。

**修复**：三处测量全部改为双端分支，对齐 m-sticky 的既有先例——Web 端保留同步测量，App / 小程序端走异步：

```ts
// #ifdef WEB
selfWidth.value = el.getBoundingClientRect().width
// #endif
// #ifndef WEB
el.getBoundingClientRectAsync()!.then((rect: DOMRect) => {
	selfWidth.value = rect.width
})
// #endif
```

两处细节值得展开：

**先问「测量结果真的被消费吗」**。修复过程中重新审视了 `measureWidth` 的调用面：`selfWidth` 实际只被 freeLine 布局（独立底部条平移）与 swipeable（轨道平移 / 手势阈值）消费，其余场景测了也白测。于是加了一行提前返回——

```ts
function measureWidth() {
	if (!freeLineMode.value && !props.swipeable) return
	// ...
}
```

这一行使大部分场景彻底跳过测量，比把整条链路全量异步化更省，也缩小了异步时序的暴露面。

**异步批量的收敛判定**。scrollspy 滚动判定要对全部内容块测量顶边位置后统一比较，异步化后 N 个 Promise 各自回调，需要收集齐再判定。用局部 `pending` 计数器解决：

```ts
const tops = new Map<number, number>()
let pending = 0
for (let i = 0; i < items.length; i++) {
	const el = ctx.paneEls.get(items[i].key)
	if (el == null) continue
	pending++
	el.getBoundingClientRectAsync()!.then((rect: DOMRect) => {
		tops.set(i, rect.top)
		pending--
		if (pending == 0) applyScrollSpy(tops)
	})
}
```

判定逻辑本身抽成 `applyScrollSpy(tops)`，与 Web 同步路径共用一份实现，双端只剩「测量方式」这一处差异。

**产物级验证捷径**：小程序端的运行时复现需要微信开发者工具，但编译产物可以静态核对——`cli publish --platform mp-weixin` 编译后 grep 产物 `getBoundingClientRect[A-Za-z]*` 调用，同步调用数应为 0。这能在不打开开发者工具的情况下先排除一类回归。

## 三、坑 2：滚动 / 收缩布局的下划线偏移半个条宽

**现象**：标签数超过 `swipe-threshold` 触发滚动布局（或 `shrink` 收缩布局）时，激活下划线明显偏右——默认 `line-width: 40px` 时恰好偏 20px，即半个条宽。

**排查**：平分布局的激活下划线是独立底部条，定位正确；滚动 / 收缩布局的下划线是标题内嵌条，样式为 `left: 50%`。问题就在这：**`left: 50%` 钉住的是条的左缘，没有回退自身半宽做居中**。平分布局那条不受影响，是因为它的定位走的是另一套实测坐标路径。

**修复**：一行补齐居中回退——

```scss
position: absolute;
bottom: 0;
left: 50%;
/* left: 50% 钉的是条左缘，须回退自身半宽居中（translateX 相对自身宽，适配任意 line-width） */
transform: translateX(-50%);
width: $m-tabs-line-width;
```

`translateX(-50%)` 的百分比相对自身宽度，随 `line-width` 主题变量自适应，全端支持——不需要为任意条宽写死偏移量。

## 四、坑 3：标签栏横向滚动整个失效——废弃属性与被裁掉的滚动区域

**现象**：滚动布局中激活标签永远贴边裁切、无法居中，标签栏也无法手动横向滚动——演示文案承诺的「自动横向滚动并居中」完全不成立。

**排查**（三层洋葱，逐层见底）：

第一层，直觉修复无效。起初以为是 `scroll-into-view` 的语义局限——它只能把元素滚到起始位置（末位标签永远贴边），于是改为程序化 `scroll-left` 居中：定位激活标题元素、测量其中心与视口中心的偏差、写入 `:scroll-left`。实测纹丝不动。

第二层，读运行时源码。插桩确认 prop 值已正确传入后，直接翻 HBuilderX 内 uni-h5 vapor 构建的 scroll-view 实现：`_scrollLeftChanged` 被 `realScrollX` 门控，而 `realScrollX` 只认 `direction` 属性——**`scroll-x` 已废弃**（uni-app x 改用 `direction`，默认 `vertical`），仅设 `scroll-x` 时内部滚动层 `overflow-x` 为 `hidden`，横向的一切滚动（触摸、`scroll-left`、`scroll-into-view` 的 X 分支）全部被禁。

第三层，钳制恒为零。补上 `direction="horizontal"` 后依然不滚。取证发现内部滚动层 `scrollWidth == offsetWidth`——**标题行（view 默认 `overflow: hidden`）把溢出的标题裁在了自己内部**，scroll-view 的滚动区域根本看不到溢出内容，源码里的钳制公式 `scrollToValue > scrollWidth - offsetWidth` 恒成立，一切滚动目标被压回 0。

**修复**（三处，缺一不可）：

```html
<scroll-view
	class="m-tabs__nav-scroll"
	:direction="canScroll ? 'horizontal' : 'none'"
	:scroll-left="navScrollLeft"
	:scroll-with-animation="true"
	ref="navScrollRef"
	@scroll="onNavScroll"
>
```

1. **`:scroll-x` 改 `:direction`**：可滚动时 `horizontal`，恢复内部滚动层的 `overflow-x: auto`；
2. **标题行 `overflow: visible`**：放行溢出标题，裁剪交回 scroll-view 真实滚动层，滚动区域恢复真实内容宽度；
3. **`scroll-into-view` 改程序化居中**：按 id 深度优先定位激活标题元素（Web 端 scroll-view 有编译器内部包装层，不能假设直接子节点结构），测量标题中心与视口中心的偏差后经 `scroll-left` 属性驱动滚动；`@scroll` 回灌镜像实际位置（手动滚动后同值目标也能重新触发），超界由 scroll-view 内部钳制，`scroll-with-animation` 提供平滑过渡。

**验证数据**：窄视口（390px）自动化实测——初始激活第 5 个标签，加载后自动滚动 153px 精确居中；点击第 7 个标签，动画结束后滚动位置偏差 0.5px（半像素内）；控制台零报错。

## 五、坑 4：带 nav 插槽时下划线偏移——均匀槽位公式的前提被打破了

**现象**：平分布局（独立底部条）在加了 `nav-left` / `nav-right` 插槽后，激活下划线明显偏左约半个条宽。

**排查**：独立底部条的定位走的是均匀槽位公式 `(i + 0.5) * 容器宽 / 标签数`——这个公式隐含一个前提：**标题行内没有任何额外占位**。插槽区块（每个 36px）加入后，标签实际中心整体右移，公式算出的槽位中心还停在原均匀分布位置，两者失差恰好接近半个条宽。

**修复**：放弃公式，改测量制——按 id 深度优先定位激活标题元素，实测其中心相对底部条定位父级的偏移。这里还埋着第二个细节：底部条与标题行**分属 nav 的不同子树**（标题行在 scroll-view 内，底部条与 scroll-view 平级），测量基准必须取底部条自己的定位父级（nav 原点），与渲染原点（`left: 0` + `translateX`）严格一致——基准取错子树，偏移不缩反增。

```ts
const navEl = el.parentElement  // 底部条的定位父级（nav），与渲染原点一致
const titleEl = findDescendantById(navEl, 'm-tabs-tab-' + newIndex.toString())
// 实测标题中心 - nav 原点 - 半条宽
applyLine(el, trect.left + trect.width / 2 - navRect.left - lw / 2)
```

测量制对插槽有无、标题行是否滚动、标签数多少全部不敏感——凡是「元素真实位置」与「公式推算位置」可能分叉的场景，实测都比公式可靠。

## 六、坑 5：scrollspy 点击标签纹丝不动——裸 scrollTo 被解析到 window.scrollTo

**现象**：scrollspy 模式点击标签，激活态正常切换，但页面完全不滚动；控制台零报错。且滚动联动判定与视口内容错位（标签「区块 1」激活，视口却停在区块 2 的内容中段）。

**排查**（两层）：

第一层，一行裸调用的静默劫持。点击处理器里写的是 `scrollTo(index)`——而 `scrollTo` 并不是组件里的函数，它只是 `defineExpose({ scrollTo: ... })` 对象字面量的**属性名**。Web 构建下这个裸调用被静默解析到**全局 `window.scrollTo`**：索引 `1` 被当作滚动坐标 `window.scrollTo(1)`，在 scroll-view 滚动的页面里等于完全无效，且不抛任何错。这是最典型的「编译期合法、运行期无害、功能全灭」三连。修复只是一行——改调真正的 `scrollToIndex`：

```ts
if (props.scrollspy) {
    setActive(index)
    scrollToIndex(index)  // 此前误写 scrollTo(index)——那是 defineExpose 的属性名，Web 端解析到 window.scrollTo
    return
}
```

第二层，基准线语义错位。修完调用后点击能滚了，但激活态仍与内容错位。取证发现两套坐标混用：scrollspy 判定直接拿 `offset-top` 作基准线（纯视口语义），而内容区实际处于**非零视口偏移的滚动容器**中（页面顶部有 44px 固定导航，滚动容器顶边在视口 44px 处）——判定整体错位一个容器偏移，标签要等内容多滚 44px 才激活，正是截图里「区块 1 激活、内容显示区块 2」的来源。另外判定不能用标签栏实时 rect：scroll 事件触发判定的瞬间，m-sticky 的吸附态可能尚未切换，标签栏还停在文档流位置——基准线会随吸附时序漂移。

**修复**：判定与点击定位统一以「吸顶标签栏底边」为基准线，用一组**稳定量**拼出吸附位（滚动容器顶偏移 + `offset-top` + 标签栏高），与吸附切换时序彻底解耦：

```ts
// 判定基准线：吸附态标签栏底边 = 滚动容器顶 + offset-top + 标签栏高
applyScrollSpy(tops, holderTop + props.offsetTop + navH)
// 点击定位：目标 = 基准线（pane 顶贴住吸顶标签栏底边），容器顶偏移在视口坐标推导中自然抵消
const scrollBy = delta - props.offsetTop - navHeight
```

**验证数据**：点击「区块 2」后滚动 288px，目标内容块顶边 131.67px，吸顶标签栏底边 132px，偏差 0.33px（半像素内）；激活态与视口内容严格一致。

## 七、共同教训：为什么这五个坑全都「零报错」

| 坑 | 层面 | 暴露方式 |
| --- | --- | --- |
| 同步测量 API 缺失 | 平台 API 差异 | 运行时 TypeError，编译器静默 |
| TypeError 中断同 hook 后续初始化 | 错误的级联效应 | 症状与根因相距很远 |
| left: 50% 未回退半宽 | CSS 定位语义 | 纯视觉偏移，功能「看起来正常」 |
| scroll-x 废弃属性 + view 默认 overflow hidden | 属性废弃 + 溢出裁剪叠加 | 功能静默失效，「看起来该滚的时候不滚」 |
| 均匀槽位公式假设无额外占位 | 公式前提与真实布局分叉 | 插槽场景视觉偏移 |
| 裸调用解析到 window.scrollTo | 标识符解析 + 静默劫持 | 功能全灭，控制台零报错 |
| 判定基准线混用两套坐标 | 坐标系 / 容器偏移错位 | 激活态与视口内容不一致 |

**「本地编译通过 + Web 端正常」不代表全端可用**（0.3.1 的结论再次成立）。小程序端的 API 支持差异不会在任何编译日志里留痕，只有真机 / 开发者工具实测能暴露。绝对定位的居中（`left: 50%`）必须搭配 `translateX(-50%)` 才成立。

**「prop 传了、DOM 属性也对，但功能不生效」时，直接读运行时源码**（坑 3 的方法论收获）。uni-h5 的 scroll-view 在根元素上用 `Object.defineProperties` 重定义了 `scrollLeft` 的 getter/setter、把 prop 变更全部收口到 `_scrollLeftChanged` 并用 `realScrollX` 门控——这些实现细节不在任何文档里，但决定了「哪些写法有效、哪些被静默吞掉」。另一条：**中间层自己的 overflow hidden 会把溢出内容从外层滚动区域里「藏起来」**——滚动容器的直接内容若被一个默认裁剪的 view 包裹，外层一切滚动机制都会因「看不到溢出」而失效。

**凡是元素真实位置可能与公式推算分叉的场景（插槽、动态占位、滚动偏移），一律实测**（坑 4）。公式只在前提成立时等于真相。

**凡是被 expose 的能力，调用点必须显式引用组件内符号**（坑 5）。`defineExpose` 的属性名在组件作用域里不可见，裸调用会被 Web 构建静默解析到全局同名 API——`window.scrollTo` 恰好存在，所以连 ReferenceError 都没有，UTS 强类型在 Web 目标下也拦不住这一类。而 scrollspy 基准线的修复再次强调：**涉及时序的状态（吸附切换）绝不能直接当测量基准**，要用与该时序无关的稳定量拼出等价值。

修复顺序上的经验依然成立：先查「测量结果真的被消费吗」——跳过无消费的测量比全量改造异步链路代价小得多，还顺带把异步时序问题的暴露面收窄到真正需要测量的两个场景。
