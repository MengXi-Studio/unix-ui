# @meng-xi/unix-ui v0.4.1 发布：m-tabs 修复批次——小程序端没有同步测量 API，以及下划线偏了半个条宽

> v0.4.1 是一个纯修复版本，聚焦 v0.4.0 新增的 m-tabs：微信小程序端 mounted 即抛 `TypeError` 导致首屏无激活标签、滚动 / 收缩布局的激活下划线整体偏移半个条宽。第一个问题来自社区 issue 实测反馈——又是「编译器不告诉你」系列：本地编译、Web 端、App 端全部正常，只有小程序端在运行时炸掉。本文带排查过程与修复代码，把这两个坑讲透。

## 一、为什么单独发一个修复版本

v0.4.0 发布 m-tabs 时，微信小程序端尚未实测（平台支持表里明确标注「本版本未实测」）。issue #5 的反馈在开发者工具里一跑就命中：**小程序端打开任何带 m-tabs 的页面，首屏没有激活标签、底部条不显示**。

排查后确认是两类问题：一个是平台 API 差异（致命，阻断初始化），一个是 CSS 居中遗漏（视觉偏移）。都已源码层修复，Web 端行为不变。

## 二、坑 1：小程序端 UniElement 没有同步 getBoundingClientRect

**现象**：m-tabs 演示页在小程序端首屏无激活态、底部条缺失；控制台抛 `TypeError: el.getBoundingClientRect is not a function`。

**排查**：m-tabs 的 `measureWidth`、scrollspy 滚动判定、点击定位三处都在 mounted / 滚动链路里同步调用 `el.getBoundingClientRect()`。Web 与 App 端的 `UniElement` 都有同步测量，唯独小程序端只提供 `getBoundingClientRectAsync`（回调 Promise）——同步方法根本不存在，调用即抛错。

更麻烦的是抛错的位置效应：**`TypeError` 中断了同一 onMounted hook 内的后续初始化**，激活态计算、底部条渲染全部没执行。症状（首屏无激活标签）与出错代码（宽度测量）相距很远，仅看表象根本对不上号。

**修复**：三处测量全部改为双端分支，对齐 m-sticky 的既有先例——Web 端保留同步测量，App / 小程序端走异步：

```ts
// #ifdef WEB
selfWidth.value = el.getBoundingClientRect().width
// #endif
// #ifndef WEB
el.getBoundingClientRectAsync()!.then((rect: DOMRect) => {
	selfWidth.value = rect.width
})
// #endif
```

两处细节值得展开：

**先问「测量结果真的被消费吗」**。修复过程中重新审视了 `measureWidth` 的调用面：`selfWidth` 实际只被 freeLine 布局（独立底部条平移）与 swipeable（轨道平移 / 手势阈值）消费，其余场景测了也白测。于是加了一行提前返回——

```ts
function measureWidth() {
	if (!freeLineMode.value && !props.swipeable) return
	// ...
}
```

这一行使大部分场景彻底跳过测量，比把整条链路全量异步化更省，也缩小了异步时序的暴露面。

**异步批量的收敛判定**。scrollspy 滚动判定要对全部内容块测量顶边位置后统一比较，异步化后 N 个 Promise 各自回调，需要收集齐再判定。用局部 `pending` 计数器解决：

```ts
const tops = new Map<number, number>()
let pending = 0
for (let i = 0; i < items.length; i++) {
	const el = ctx.paneEls.get(items[i].key)
	if (el == null) continue
	pending++
	el.getBoundingClientRectAsync()!.then((rect: DOMRect) => {
		tops.set(i, rect.top)
		pending--
		if (pending == 0) applyScrollSpy(tops)
	})
}
```

判定逻辑本身抽成 `applyScrollSpy(tops)`，与 Web 同步路径共用一份实现，双端只剩「测量方式」这一处差异。

**产物级验证捷径**：小程序端的运行时复现需要微信开发者工具，但编译产物可以静态核对——`cli publish --platform mp-weixin` 编译后 grep 产物 `getBoundingClientRect[A-Za-z]*` 调用，同步调用数应为 0。这能在不打开开发者工具的情况下先排除一类回归。

## 三、坑 2：滚动 / 收缩布局的下划线偏移半个条宽

**现象**：标签数超过 `swipe-threshold` 触发滚动布局（或 `shrink` 收缩布局）时，激活下划线明显偏右——默认 `line-width: 40px` 时恰好偏 20px，即半个条宽。

**排查**：平分布局的激活下划线是独立底部条，定位正确；滚动 / 收缩布局的下划线是标题内嵌条，样式为 `left: 50%`。问题就在这：**`left: 50%` 钉住的是条的左缘，没有回退自身半宽做居中**。平分布局那条不受影响，是因为它的定位走的是另一套实测坐标路径。

**修复**：一行补齐居中回退——

```scss
position: absolute;
bottom: 0;
left: 50%;
/* left: 50% 钉的是条左缘，须回退自身半宽居中（translateX 相对自身宽，适配任意 line-width） */
transform: translateX(-50%);
width: $m-tabs-line-width;
```

`translateX(-50%)` 的百分比相对自身宽度，随 `line-width` 主题变量自适应，全端支持——不需要为任意条宽写死偏移量。

## 四、两个问题的共同教训

| 坑 | 层面 | 暴露方式 |
| --- | --- | --- |
| 同步测量 API 缺失 | 平台 API 差异 | 运行时 TypeError，编译器静默 |
| TypeError 中断同 hook 后续初始化 | 错误的级联效应 | 症状与根因相距很远 |
| left: 50% 未回退半宽 | CSS 定位语义 | 纯视觉偏移，功能「看起来正常」 |

第一个坑再次印证 0.3.1 的结论：**「本地编译通过 + Web 端正常」不代表全端可用**。小程序端的 API 支持差异不会在任何编译日志里留痕，只有真机 / 开发者工具实测能暴露。第二个坑则提醒：绝对定位的居中（`left: 50%`）必须搭配 `translateX(-50%)` 才成立，这条在「实测截图比对」环节一目了然。

另一个方法论收获是修复顺序：**先查「测量结果真的被消费吗」，再谈异步化**。跳过无消费的测量比全量改造异步链路代价小得多，还顺带把异步时序问题的暴露面收窄到真正需要测量的两个场景。
