# @meng-xi/unix-ui v0.4.2 发布：m-tabs 修复——小程序端 UniElement 的 DOM 能力是零、Web 端滚动条藏不住

> v0.4.2 是一个纯修复版本，聚焦 v0.4.1 发布后的两条社区与实测反馈：其一，m-tabs 微信小程序端崩溃（[#8](https://github.com/MengXi-Studio/unix-ui/issues/8)）——开启 `shrink` 或标签数超过阈值的实例，进入页面即抛 `Cannot read properties of undefined (reading 'length')`，首屏激活态初始化被跳过，根因是 0.4.1 没修完的另一半：**小程序端 UniElement 的 DOM 能力是零**——没有 `children`、没有 `parentElement`，而 0.4.1 引入的异步测量还只认有 id 的元素；其二，Web 端滚动布局的标签栏在横向滚动时露出浏览器默认滚动条——uni-h5 运行时的 `show-scrollbar="false"` 形同虚设。本文带取证过程与修复方案。

## 一、现象与取证

0.4.1 修复了 #5（小程序端没有同步测量 API），但 `canScroll` 实例（shrink 或标签数超过 `swipe-threshold`）在开发者工具里一跑就崩：

```
TypeError: Cannot read properties of undefined (reading 'length')
    at findDescendantById (m-tabs.js:170)
    at centerActiveTab (m-tabs.js:372)
```

`mounted` 与 `activeIndex` watcher 两条路径都抛，激活初始化被中断——和 #5 同款「位置效应」：崩在 mounted，症状却满页面都是。

取证方式与 #5 一致：直接读小程序端产物里的 `UniElement` 实现类（`common/vendor.js`）。两个关键事实：

1. **`children` 和 `parentElement` 根本不存在**。实现类只有 `getBoundingClientRectAsync` / `getAttribute` / `setAttribute` / `scrollTo` / `animate`，连 `scrollHeight` / `offsetHeight` 都恒为 NaN——小程序逻辑层不开放 DOM，子树和祖先都遍历不了。而 m-tabs 的 `findDescendantById`（按 id 找标题元素）靠 `el.children` 深度优先遍历，`findScrollParent`（scrollspy 探测滚动容器）靠 `parentElement` 向上爬——在 `undefined` 上取属性或读 `length`，崩得干干净净。
2. **`getBoundingClientRectAsync` 只对有 id 的元素生效**。它的内部实现就是 `createSelectorQuery().in(this.$vm).select('#' + this.id)`，无 id 的元素直接 `console.warn` 并 reject。也就是说即使把崩溃点全修了，凡是补不上 id 的元素，0.4.1 引入的异步测量路径在小程序端依旧空转。

#8 的反馈里把这两点都指了出来，与我们的取证完全一致。

## 二、修复（三处配套，缺一不可）

**1. 遍历型查找编译期降级**：`findDescendantById` / `findScrollParent` 小程序端直接返回 `null`（调用点本就判空，居中 / 定位优雅跳过）。注意两个必须一起修——只修 `findDescendantById` 的崩溃点，`findScrollParent` 就是下一个雷。

**2. 小程序端测量统一走 id 查询**：新增 `queryRectById`——

```ts
uni.createSelectorQuery().in(instance.proxy)
	.select('#' + id)
	.boundingClientRect()
	.exec((ret: Array<any>) => {
		const first = ret.length > 0 ? ret[0] : null
		cb(first as DOMRect | null)
	})
```

全端 UTS API（官方文档签名明确），`in(instance.proxy)` 限定**组件实例作用域**——id 只需组件内唯一，多实例安全。为此给标签栏 / 底部条 / 根节点补了静态 id，内容块（m-tab pane）按注册序动态 id，标题的 `m-tabs-tab-N` 天然满足。滚动布局激活居中、插槽布局底部条定位、scrollspy 滚动判定与点击定位在小程序端全部恢复——不是只不崩。

**3. 能力降级显式声明**：底部条切换动画小程序端直接落位（`UniElement.animate` 的 transform keyframes 支持未证实，位置正确优先）；scroll-view 内嵌场景的 scrollspy 判定与点击定位按页面级滚动语义退化（滚动容器不可探测，`uni.pageScrollTo` 兜底）。

## 三、坑 2：Web 端滚动条藏不住——show-scrollbar 形同虚设

**现象**：滚动布局的标签栏（0.4.1 修复滚动失效后）在 Web 端横向滚动时，下方露出一条浏览器默认滚动条。

**取证**：`show-scrollbar="false"` 在 uni-h5 运行时（vapor 与 VDOM 构建皆然）的实现只是给内部滚动层追加 `uni-scroll-view-scrollbar-hidden` 类——**隐藏滚动条的 CSS 在运行时样式表里完全缺失**（`::-webkit-scrollbar` 全库 0 处），这个 prop 在 Web 端形同虚设。

**修复**（两处）：标签栏 scroll-view 显式 `:show-scrollbar="false"`（App 端语义生效）；Web 端组件内兜底——`#ifdef WEB` 条件编译内以 `scrollbar-width: none` + `::-webkit-scrollbar` 双覆盖内部真实滚动层（包装节点非模板节点，须后代选择器穿透；仅 Web 端编译，不受 App 端 ucss 约束）。实测滚动条占高为 0、横向可滚性保持。

## 四、教训

**平台能力差异要一次查到底，不能只修报错的那一处**。`children` / `parentElement` 缺失、异步测量只认 id，是「小程序端 UniElement DOM 能力为零」这一个根因的多种表现——0.4.1 修 #5 时只处理了「没有同步测量」，没意识到小程序端连 DOM 遍历都没有，于是修一个崩一个。读运行时产物里的类实现（vendor.js）比任何文档都快。

另一条：`createSelectorQuery().in(instance)` 按组件实例作用域查 id 是小程序端测量的正路——**多实例安全**这一性质由 `in()` 保证，而不是靠全局唯一 id。滚动条坑则再次印证：prop 的承诺要靠运行时的实现兑现，**「传了 prop 没生效」先看运行时样式表 / 实现类里对应机制是否真的存在**。

## 五、质量验证

- **mp-weixin 产物静态核对**：`el.children` 零残留，`queryRectById`（createSelectorQuery 组件作用域查询）正确生成，全部补齐 id（root / nav / line / nav-scroll / pane）落到 wxml
- **Android VDOM 产物静态核对（appResource 导出）**：`#ifdef MP` 分支零残留，App 端声明序与上轮验证版本等价
- **Web 滚动条实测（puppeteer）**：滚动布局标签栏真实滚动层 `scrollbar-width: none` 命中、`uni-scroll-view-scrollbar-hidden` 类挂上、横向滚动条占高为 0（clientHeight == offsetHeight == 44）、可滚性保持
- **Web 全量回归**：全部变体行为不变（修复仅影响小程序端与 Web 样式条件编译分支）；`sync:uni-modules:check` 与 `build:docs`（VitePress 死链检查）通过
