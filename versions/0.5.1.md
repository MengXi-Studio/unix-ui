# @meng-xi/unix-ui v0.5.1 发布：修复 m-tabs 平分模式小程序端首帧底部条贴左

> v0.5.1 是一个只含一项修复的补丁版本：0.5.0 为 options 形态 tabs 补的首帧定位在微信小程序端仍会失效——渲染层首次提交晚于逻辑层 `nextTick`，同步查询拿不到节点且不重试，底部条停在最左缘（[#13](https://github.com/MengXi-Studio/unix-ui/issues/13)）。本版本将小程序端的首定位改为四档递增重试，Web / App 分支保持原逻辑不变。

## 一、问题：0.5.0 的修复只覆盖了 Web 与 App

0.5.0 修过同一个现象（[#10](https://github.com/MengXi-Studio/unix-ui/issues/10)）：options 形态没有 `m-tab` 子组件，`ctx.items` 恒为空，`watch(ctx.items)` 里的 `animateLine` 不会触发；初始 `activeIndex` 与解析结果相同也不会触发 `watch(activeIndex)`，`lineLeft` 保持初值 0，首屏底部条贴在标签栏最左缘，点击任意标签后才归位。

当时在 `onMounted` 末尾补了一次 `nextTick` 首定位，Web 与 App 端恢复正常。但 0.5.0 发布后，微信小程序端仍能复现：进入页面不点击，底部条依旧贴左。

## 二、根因：`nextTick` 等到的是逻辑层，不是渲染层

- **时序**：小程序端 `nextTick` 只保证逻辑层完成更新，渲染层首次 `setData` 尚未提交，此时节点还不存在于渲染树中；
- **查询语义**：节点查询（`queryRectById`）在小程序端是异步的，查不到 `#m-tabs-nav` / `#m-tabs-tab-<i>` 时**静默返回**，无法从返回值判断成功与否，也就不会触发重试；
- **结果**：`animateLine` 内部拿不到宽度与偏移，直接提前返回，`lineLeft` 保持 0；点击标签后由用户交互重新走一次测量，才「突然」归位。

这不是定位算法的问题，而是「测量时机」与「渲染提交时机」的错配。固定一次 `nextTick` 在 Web / App 成立，在小程序不成立。

## 三、修复：四档递增重试 + 幂等定位

小程序端改为按 0 / 16 / 50 / 120ms 递增重试，覆盖渲染层首帧提交的时间窗口；Web / App 继续走原来的 `nextTick`：

```uts
// #ifdef MP
// 小程序端渲染层首次提交晚于逻辑层 nextTick，createSelectorQuery 可能查不到刚挂载的节点，
// 且 queryRectById 查不到时静默返回（无法感知是否成功）：按 0 / 16 / 50 / 120ms 递增重试，
// 成功后的重复调用 from == to，仅重设同一位置，无副作用
const initLineDelays: number[] = [0, 16, 50, 120]
for (let i = 0; i < initLineDelays.length; i++) {
	setTimeout(() => {
		animateLine(activeIndex.value, activeIndex.value)
	}, initLineDelays[i])
}
// #endif
// #ifndef MP
nextTick(() => {
	animateLine(activeIndex.value, activeIndex.value)
})
// #endif
```

关键点是**幂等**：首次成功定位后，后续重试调用 `animateLine(i, i)` 的起点与终点相同，只是把同一个 `lineLeft` 再写一遍，不会产生位移动画或闪烁。因此不需要维护「是否已成功」的标志位，也不需要在小程序端引入额外的状态机。

## 四、为什么是「递增重试」而不是固定延迟

- **固定单次延迟**（如统一 100ms）：低端机冷启动首帧可能超过这个窗口，仍会失败；调大到 300ms 又会让所有机型的首帧定位都变慢；
- **无限轮询**：节点一旦因条件渲染始终不存在，轮询会持续消耗查询开销，且没有可靠的终止条件（查询失败无返回值）；
- **四档递增**：0ms 覆盖渲染层已就绪的常规情况，16ms / 50ms / 120ms 覆盖首帧提交与字体、布局完成的不同节奏；最多四次查询，成本可控，且成功后的重复调用无副作用。

代价是极慢机型上首帧底部条可能晚约 120ms 归位。考虑到它发生在页面首次进入、且期间用户尚未交互，这比「一直贴左直到点击」更可接受。

## 五、回归范围与验证边界

- **代码级核对**：Web / App 分支与 0.5.0 完全一致（仅把原 `nextTick` 包进 `#ifndef MP`），不存在行为变化；
- **影响面**：仅 `m-tabs` 的 options 形态 + 平分布局（标签数未超过 `swipe-threshold` 且未开启 `shrink`）+ 小程序端；其余形态（子组件 `m-tab`）由 `watch(ctx.items)` 与布局回调驱动，不经过这条首定位路径；其他组件无改动；
- **待复测**：微信开发者工具 / 真机首次进入页面（不点击）时底部条的落位，以及支付宝、抖音小程序同链路的渲染时序。本版本无 API、事件与主题变量变更，复测只需覆盖首屏表现。

## 六、从 0.5.0 升级

```bash
pnpm add @meng-xi/unix-ui@latest
# 将包内容拷贝覆盖 uni_modules/m-ui-x
```

- 无破坏性变更：仅 `m-tabs` 内部定位逻辑调整，props / events / 插槽 / 主题变量均未改动；
- 仅使用 Web 或 App 的项目升级后行为与 0.5.0 一致，可按需升级。
