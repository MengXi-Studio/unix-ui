# @meng-xi/unix-ui v0.5.3 发布：修复小程序端重复插槽告警（日历 / 日期横条 / 级联）

> v0.5.3 是一个只含修复的补丁版本：日历日格 `v-for` 内的具名插槽在微信小程序端被判定为「同一实例内多个同名插槽」，一次打开弹层刷约 2000 行告警，且自定义内容只有第一个格子生效（[#17](https://github.com/MengXi-Studio/unix-ui/issues/17)）。修复的同时对全库 46 个组件做了同模式审计，日期横条与级联选择存在同样结构，一并处理。

## 一、问题：告警刷屏，插槽只生效一次

使用默认形态就能复现，宿主不需要传任何插槽：

```html
<m-calendar-popup v-model:show="show" type="single" title="选择日期" />
```

打开弹层后，微信开发者工具控制台出现大量重复告警：

```
[Component] More than one slot named "top-info" are found inside a single component instance
(in component "uni_modules/m-ui-x/components/m-calendar/m-calendar"). The first one was accepted.
```

`bottom-info` 同时出现，一次打开约 2000 行。更麻烦的是功能层面：宿主确实传了 `top-info` 时，也只有第一个日格渲染出自定义内容，其余 41 格保持默认。

## 二、根因：同名插槽在单实例内只能有一个

两个因素叠加：

1. **模板结构**：`m-calendar-panel` 在日格 `v-for` 内直接声明 `<slot name="top-info">` / `<slot name="bottom-info">`，单个月面板实例里就有 42 个同名 outlet。微信规定同一组件实例内插槽名唯一，只接受第一个，其余全部告警。
2. **插槽判定**：面板是否渲染信息行由 `cfg.hasTopInfoSlot` 决定，而它来自 `slots['top-info'] != null`。微信端的 `useSlots()` 按静态编译结果返回，宿主没传内容也可能是 `true`——所以「没传插槽也会刷屏」。
3. **转发链路**：`m-calendar` 与 `m-calendar-popup` 用 `v-if="$slots['top-info'] != null"` 逐层转发，静态误判会把这个空插槽一路传到面板。

问题不在插槽内容，而在「插槽 outlet 被放进了循环」。

## 三、为什么不抽成子组件

issue 的第一条建议是把日格抽成 `<m-calendar-day-cell>`，让每个实例只有一个 `top-info`。这个思路在 Vue 里成立，但在当前架构下不解决告警：

- 面板仍需在 `v-for` 内渲染 42 个日格组件；
- 要把宿主的插槽内容传给每个日格，面板模板里必须写 42 份 `<m-calendar-day-cell><template #top-info>…</template></m-calendar-day-cell>`；
- 这 42 份仍会编译成面板实例内的 42 个同名插槽 outlet，告警原样存在，只是从「42 个 slot 标签」变成「42 个转发模板」。

根因是微信小程序「单实例同名插槽唯一」的静态约束，任何「按项重复声明插槽」的写法都绕不开。因此采用平台分叉：小程序端不再在循环内声明插槽。

## 四、修复：小程序端循环内不使用插槽

面板模板按平台拆分，Web / App 保持原逻辑，小程序端回退为内置文本：

```html
<!-- #ifndef MP -->
<view v-if="isRealDay(day) && (day.topInfo != '' || cfg.hasTopInfoSlot)" class="m-calendar__day-info">
	<slot name="top-info" :day="day">
		<text :class="dayInfoTextCls(day)">{{ day.topInfo }}</text>
	</slot>
</view>
<!-- #endif -->
<!-- #ifdef MP -->
<view v-if="isRealDay(day) && day.topInfo != ''" class="m-calendar__day-info">
	<text :class="dayInfoTextCls(day)">{{ day.topInfo }}</text>
</view>
<!-- #endif -->
```

同批处理的位置：

| 组件 | 循环内插槽 | 小程序端替代 |
| --- | --- | --- |
| m-calendar-panel | `month-title` / `text` / `top-info` / `bottom-info` | 月标题、日号、上下信息全部走内置文本 |
| m-calendar · m-calendar-popup | 上述四个插槽的转发 | 小程序端不再转发，避免向不存在的插槽传内容 |
| m-date-strip | `item` / `top-info` / `bottom-info` | `formatter` 的 `text` / `topInfo` / `bottomInfo`；`show-lunar` 经 `bottomInfo` 仍正常显示 |
| m-cascader · m-cascader-popup | `option` / `options-top` / `options-bottom` | `field-names` 的 `labelKey` 决定选项文案 |

小程序端信息行还顺手去掉了 `cfg.hasTopInfoSlot` 判断——该值在微信端不可靠，改用「确实有文本才渲染」，避免出现空的占位行。

## 五、全库审计：只有这三处

按「具名插槽 outlet 是否声明在 `v-for` 内」逐个检查全部含插槽的组件：

| 组件 | 结论 |
| --- | --- |
| m-calendar-panel / m-calendar / m-calendar-popup | 本轮修复 |
| m-date-strip | 本轮修复 |
| m-cascader / m-cascader-popup | 本轮修复（`option` 为无条件声明，风险最高） |
| m-tabs | 安全：`nav-left` / `nav-right` 在循环外，sticky 与非 sticky 分支同时只渲染一个 |
| m-loading | 安全：`icon` 插槽在循环外，`v-for` 只用于默认辐条 |
| m-flex-item / m-space-item | 安全：仅默认插槽 |
| m-cell / m-image / m-grid-item / m-badge / m-checkbox-popup | 安全：插槽均不在循环内 |

## 六、代价与替代方案

小程序端不再支持「每个日格 / 选项完全自定义节点」，这是微信插槽机制决定的，无法在保留循环内自定义内容的同时消除告警。替代路径：

- 日历与日期横条：用 `formatter` 返回 `text` / `topInfo` / `bottomInfo`，文本能力完整；农历、范围端点文案等内置逻辑不受影响
- 级联选择：用 `field-names` 的 `labelKey` 映射选项文案
- 需要自定义节点时，可继续在 Web / App 使用插槽，或用 `custom-class` / `custom-style` 调整样式

## 七、验证

- **Web 实测**：日历弹层页打开 single 弹层后月份网格完整；日期横条页星期行与日期行正常；级联选择页层级标签与选项行正常；三页控制台均无 error / warning
- **构建与一致性**：`pnpm sync:uni-modules:check` 通过，`pnpm build:docs` 通过
- **待复测**：微信开发者工具按 #17 步骤确认告警消失（目标场景），以及小程序端月标题 / 日号 / 农历 / 选项文案的渲染完整性

## 八、从 0.5.2 升级

```bash
pnpm add @meng-xi/unix-ui@latest
# 将包内容拷贝覆盖 uni_modules/m-ui-x
```

无破坏性变更：仅小程序端的插槽渲染路径调整，Web / App 的插槽行为、全部 props / events 与主题变量均未改动。使用插槽自定义日格的项目在小程序端会退回内置文本，请按第六节改用 `formatter`。
