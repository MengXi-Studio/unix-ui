# @meng-xi/unix-ui v0.7.3 发布：修复 VDOM 模式下微信小程序具名插槽被误判为「未传入」

> v0.7.3 是一个只含修复的补丁版本，收敛 0.7.2 引入的插槽守卫回归（[#27](https://github.com/MengXi-Studio/unix-ui/issues/27)）：
> `slotHasContent` 只按「数组长度 > 0」判定，而 uni-app x **VDOM 模式**下微信小程序的具名插槽值是布尔 `true`，取不到 `length` → 判为未传入 → 调用方传入的自定义内容被 `v-if` 整块丢弃。
> 受影响的不止 `m-tabs`：所有经该守卫的具名插槽（`nav-left` / `nav-right` / `toolbar` / `title` / `confirm` / `cancel` / `columns-top` / `option` / `left` / `action` 等）在 VDOM 小程序端都会静默消失。
> 修复只在 `utils/slot.uts` 的小程序条件编译段内，Web / App 代码路径与 0.7.2 完全一致，无 API 变更、无业务侧改造。

## 一、现象

环境：HBuilderX 5.34（uni-app x，VDOM 模式）+ 微信小程序（mp-weixin）。

- 在自定义组件（非页面）中给 `m-tabs` 传入 `#nav-left` / `#nav-right`，标签栏两侧内容完全消失；
- 同环境下的 `m-picker-popup` 系列传入 `#toolbar` / `#title` / `#confirm`，自定义顶栏不渲染；
- 0.7.1 正常，升级 0.7.2 后必现；Web 与 App 端不受影响。

## 二、根因：VDOM 下插槽值是布尔 `true`，不是函数

0.7.2 新增的守卫：

```uts
export function slotHasContent(slot: any | null): boolean {
	if (slot == null) return false
	// #ifdef MP
	const list = slot as any[]
	const len = list.length
	if (len == null) return false
	return len > 0
	// #endif
	return true
}
```

它假设小程序端插槽只有「节点数组」一种形态（未传时为空数组）。

issue #27 推测 VDOM 模式下 `useSlots()` 返回的是渲染函数、`Function.length` 为 0。**实际在产物里打日志取证后，结论不同**：

```
未传插槽：slots 仅含 d,default          slots['nav-right'] === undefined
传了插槽：slots 含 nav-left,nav-right   typeof slots['nav-right'] === 'boolean'，值为 true
```

也就是说 VDOM 编译产物把小程序的插槽存在性压成了**布尔标记**：已传为 `true`，未传则没有该 key。布尔值取不到 `length`，`len == null` 直接返回 `false`，插槽内容被模板上的 `v-if` 整块吞掉。

> 取证方式：在 `unpackage/dist/dev/mp-weixin` 的 `m-tabs.js` 里临时打印 `typeof slots['nav-right']` 与 `Object.keys(slots)`，wechatide 读取 console 缓冲区确认；重新编译即还原，产物不入 git。

## 三、修复

`packages/core/utils/slot.uts` 的小程序分支改为按「值形态」分流，函数与布尔都视为「已传入」，数组仍按长度判定（保住 #24 的「空数组视为未传」）：

```uts
export function slotHasContent(slot: any | null): boolean {
	if (slot == null) return false
	// #ifdef MP
	// VDOM 模式下小程序端插槽值可能是布尔标记（已传为 true，未传则无该 key）
	// 或渲染函数（Function.length 恒为 0），存在即视为已传入（issue #27）
	if (typeof slot == 'function') return true
	if (typeof slot == 'boolean') return slot as boolean
	// 非 VDOM 模式：插槽为节点数组，未传时为空数组；空对象取不到 length，同样视为未传
	const list = slot as any[]
	const len = list.length
	if (len == null) return false
	return len > 0
	// #endif
	// #ifndef MP
	// Web / App：插槽存在即视为已传入（渲染函数），内容为空是调用方自身的选择
	return true
	// #endif
}
```

- `typeof slot == 'function'`：兼容 issue 中描述的渲染函数形态（其 `length` 为形参个数，不可用于判空）；
- `typeof slot == 'boolean'`：VDOM 模式的实际形态，直接返回该布尔值；
- 其余仍按数组长度判定，未传插槽（`undefined` / 空数组 / 空对象）行为与 0.7.2 一致，不会把空插槽转发下去覆盖默认内容。

## 四、影响范围

- 涉及 `packages/core/components` 下 **30 个组件文件、121 处具名插槽判定**，全部收敛在 `slotHasContent` 一个入口，本次只改该工具函数，组件源码未动；
- 典型受影响插槽：`m-tabs`（`nav-left` / `nav-right`）、picker-popup 系列（`toolbar` / `title` / `confirm` / `cancel` / `footer` / `columns-top` / `columns-bottom` / `option`）、`m-calendar`、`m-cascader`、`m-search`（`left` / `right-icon` / `action`）、`m-checkbox` / `m-password-input-popup` 等；
- 默认插槽（`slots['default'] != null` 判定）不经过该函数，行为不变；
- Web / App 走 `#ifndef MP` 分支，行为与 0.7.2 完全一致。

## 五、验证

**微信小程序（微信开发者工具，`mp-weixin` 产物，编译日志确认「VDOM模式」）**

- `pages-sub/nav/tabs/tabs` 的「nav-left / nav-right 插槽」卡片由空白恢复为「左 标签 1 标签 2 右」；
- 同页其他未传插槽的标签栏默认布局不变（无多余占位、无默认内容被覆盖）；
- console 无报错，调试日志已在重新编译后清除；产物 `utils/slot.js` 为三分支实现。

**工程校验**

- `pnpm sync:uni-modules` 同步、`pnpm sync:uni-modules:check` 一致性校验通过；
- `mp-weixin` 编译成功（68 页）。

**未覆盖**

- Web / App 未重跑：本次改动全部位于 `#ifdef MP` 段内，非小程序端编译产物与 0.7.2 相同；
- Android 云打包需随下一个版本统一复验。

## 六、从 0.7.2 升级

```bash
pnpm add @meng-xi/unix-ui@latest
# 将包内容拷贝覆盖 uni_modules/m-ui-x
```

- 无破坏性 API 变更，无需改业务代码；
- 若你在 0.7.2 上按 issue 建议临时规避（放弃 `nav-right` 等插槽、改为同级布局），升级后可恢复使用插槽写法；
- `utils/slot.uts` 仍为内部工具，不在公开 API 承诺范围内。
